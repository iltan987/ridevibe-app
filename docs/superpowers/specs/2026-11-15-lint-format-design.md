# Stricter linting and formatting — design (2026-11-15)

Short design: everything here was settled in conversation with iltan (approved 2026-11-15).

## Intent

1. Stop type-system bypasses: `any`, casts (`as`), non-null `!`, `@ts-*` comments and bare `eslint-disable`.
2. Let ESLint catch real bugs earlier (type-aware rules: promises, `null` printed into text, always-true conditions,
   deprecated APIs, unknown Tailwind classes).
3. Add a formatter (Prettier) with Tailwind class sorting.

**Anti-goal (iltan):** the tools must help, not block. Work that took 10 writes must not take 15. No loop of
"write → tool rewrites the file → re-read → rewrite to please the linter".

## Measured before (2026-11-14)

- `eslint-config-next` defaults only (no type-aware rules); `pnpm lint` ~13 s. Already: 0 `any` in app code (1
  justified disable), 0 `@ts-*`, 2 disables.
- `strictTypeChecked` + `stylisticTypeChecked` + `switch-exhaustiveness-check` + no casts: 599 problems in 119 files.
  229 are node:test `test()` calls (`no-floating-promises` false positives), ~130 purely stylistic
  (`no-confusing-void-expression`, `consistent-type-definitions`), ~240 worth working through (62 casts, 10 `!`,
  33 `restrict-template-expressions`, 16 `no-base-to-string`, 15 `no-unnecessary-condition`, 12 `no-deprecated`
  (React `FormEvent`), 1 `no-misused-promises`, …). Typed lint ~50 s.
- Prettier 3.10 dry run, `printWidth: 120`: 108 of 230 code files change (~1,100 lines); at 100: 145 files.

## Approaches (how the tools run)

- **A. PostToolUse hook formats after every edit.** Always-formatted files, but Prettier often rewrites the lines just
  written (class order, wrapping), so the next `Edit` on them misses and needs a re-read. Rejected: exactly the extra
  writes iltan doesn't want. An `async` hook is worse (races the next edit).
- **B. Batch once per commit (chosen).** Nothing touches files while working. Right before each commit (part of the
  existing pre-commit checks): `pnpm format` → `pnpm lint:fix` → `pnpm lint`; then review the diff of that batch. At
  most one re-read per file per commit. Subagents do the same at each of their commits.
- **C. Git pre-commit hook (husky/lint-staged).** Blocks commits and adds packages; rejected (no blocking).
  **Changed later the same day (iltan):** adopted on top of B, so the batch runs itself at `git commit` on the staged
  files (lint-staged `--no-stash`); the full lint/tsc/test/build check stays manual. See CLAUDE.md "Commands".

## Decisions

- **New dev dependencies (iltan OK):** `prettier`, `prettier-plugin-tailwindcss`, `typescript-eslint` (direct; today
  only transitive via `eslint-config-next`), `@eslint-community/eslint-plugin-eslint-comments`,
  `eslint-plugin-better-tailwindcss`.
- **Not added:** `eslint-plugin-prettier` (discouraged by Prettier and typescript-eslint; slower; formatting as lint
  errors). `eslint-config-prettier` only if a real conflict shows up after Prettier lands (current presets ship no
  formatting rules).
- **Prettier:** `printWidth: 120`, otherwise defaults (code already uses double quotes and semicolons). Plugin
  `prettier-plugin-tailwindcss` with `tailwindStylesheet: "./src/app/globals.css"` and `tailwindFunctions: ["cn"]`
  (plus `cva` if used). Scope: TS/TSX/JS/MJS, CSS, JSON. Ignored: Markdown (hand-wrapped docs and tables), SQL,
  `src/lib/supabase/database.types.ts` (regenerated by the CLI), build output. Scripts `format` and `format:check`.
  The reformat is its own commit, listed in `.git-blame-ignore-revs`.
- **Rule selection principle:** a rule stays on only if it catches a bug or a type bypass. Purely stylistic rules are
  off unless `--fix` fixes them without help.
- **typescript-eslint:** `strictTypeChecked` (type-aware, `projectService`) on TS files, plus
  `switch-exhaustiveness-check`. Off: `no-confusing-void-expression`, the `stylisticTypeChecked` preset (keep only
  autofixable members if they cost nothing). `no-floating-promises`: allow node:test's `test`/`describe`/`it`
  (`allowForKnownSafeCalls`) instead of 229 `void`s.
- **Casts (option A):** `consistent-type-assertions` with `assertionStyle: "never"` (`as const` stays allowed).
  Replace casts with Zod parsing, type guards or better types; an unavoidable cast gets a disable with a reason.
- **Disable comments:** eslint-comments `require-description` (every disable says `-- why`), `no-unlimited-disable`,
  `disable-enable-pair`; `linterOptions.reportUnusedDisableDirectives: "error"`. `@ts-*` comments stay banned
  (`ban-ts-comment`, from the preset).
- **Tailwind (`eslint-plugin-better-tailwindcss`):** entry point `src/app/globals.css`; correctness rules
  (`no-unknown-classes`, `no-conflicting-classes`, `no-concatenated-classes`) plus `no-duplicate-classes`,
  `no-deprecated-classes`, `enforce-canonical-classes`, `no-unnecessary-whitespace`. Off: its class-order and
  line-wrapping rules (Prettier owns them). Own utilities (`heading`, `eyebrow`, …) must be recognised (registered
  via `@utility` or listed in the rule's ignore option).
- **Editor:** `.vscode/extensions.json` recommends Prettier, ESLint, Tailwind CSS IntelliSense; `.vscode/settings.json`
  sets Prettier as default formatter with format-on-save (for iltan's edits; Claude formats in the batch).
- **Docs:** CLAUDE.md gets the batch step in Commands/"before every commit" and a short "write it so lint passes"
  list (no casts → Zod/guards; template values must be strings; `void` for intentional fire-and-forget; …) so code
  comes out right the first time. A `docs/learnings/` entry for lint quirks found on the way.

## Order (one branch `chore/lint-format`)

1. Prettier + class sorting + scripts + `.vscode/` + blame-ignore (mechanical reformat commit, then its hash in
   `.git-blame-ignore-revs`).
2. typescript-eslint type-aware rules, eslint-comments, cast ban; fix all hits (or justified disables).
3. better-tailwindcss; fix all hits.
4. CLAUDE.md / learnings / follow-ups (remove the "Stricter ESLint rules" and "Dead-code tool?" overlap where settled;
   the `MEMBER_STATUSES` cast item is resolved here).

## Left to the builder

replaced. Any rule that turns out noisy without catching bugs: switch it off and note why in the config.
